then tokenisers appeared

towards the end, we moved a little closer to tokenisers. that was enough to send me into the usual rabbit hole: i opened a few tabs, started looking up how tokenisation works, and somehow ended up reading about the different ways text gets broken down before a language model sees it.

the basic problem is pretty simple. a language model does not read a sentence as a sentence. it needs numbers. a tokeniser turns text into small pieces and maps those pieces to token ids.

the useful mental model: text -> tokens -> token ids -> the model.

the bpe rabbit hole

bpe, or byte pair encoding, was the one that pulled me in. the rough idea is very readable:

i mostly knew how bpe works already, at least in the “yeah, it merges frequent pairs” kind of way. but that is exactly the sort of knowledge that becomes dangerous when you start implementing it. so i decided to pretend i knew nothing and start from square zero.

  1. start with small units, usually bytes;
  2. find the pair that appears most often;
  3. merge that pair into a new token;
  4. repeat until the vocabulary reaches the size you want.

repeated patterns gradually become useful chunks. a frequent piece like ing might become one token, but a rare or new word can still fall back to smaller pieces. during encoding, the learned merges are applied again to turn new text into token ids. decoding reverses that process.

this sounds simple enough until you start thinking about unicode, bytes, whitespace, special tokens, merge ordering, vocab files, and all the little edge cases hiding behind “just split the text”. classic.
